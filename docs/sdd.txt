System Design Document: House Phone

1. Executive Summary

House Phone is a dedicated, distraction-free edge device that replaces your
smartphone once you're home. Built on the Elecrow ESP32-S3 3.5" touchscreen
module (the same hardware the project started on as "Jarvis Edge Node"), it
acts as a modern landline terminal and smart-home command center: it relays
phone notifications over BLE, controls Tapo smart lighting directly over the
LAN, runs cooking timers and a bedside alarm, and still captures local AI
voice notes through the original Jarvis dual-tier LLM pipeline. See
docs/new_idea.txt for the original pivot proposal this document implements.

2. System Architecture

The system operates across four tiers:

2.1 Edge Device (ESP32-S3 Firmware)

Role: Data capture, UI rendering, offline storage, BLE notification relay,
direct local timers/alarms.

Hardware: Elecrow CrowPanel Advance 3.5" ESP32-S3 (ILI9488 480x320 SPI
panel, GT911 capacitive touch, onboard PDM microphone, microSD).

Core Logic: C++ (Arduino framework via PlatformIO).

UI Framework: LVGL v9 — a persistent status bar over a horizontal
`lv_tileview` carousel, "Digital Sanctuary" style (see section 3).

Connectivity: WiFi (HTTP to the backend, MQTT for push-back) and a BLE GATT
server (receives Tasker-relayed Android notifications). WiFi + BLE run
concurrently on the ESP32's shared radio via the IDF's built-in coexistence
handling — no extra firmware work is required for that, but expect BLE
throughput to dip during a large WiFi upload (e.g. a queued voice note
syncing) and vice versa.

Offline Queue: microSD card (dedicated SPI3/HSPI bus) stores `.wav` voice
recordings pending upload, and persists on-device settings (WiFi/backend/
MQTT/alarm config) as simple key=value text files.

2.2 Home Server Backend (FastAPI / Python)

Role: Central hub — AI routing, database, MQTT broker communication, and
Tapo bulb control (docs/coding.txt 2.1 — keep the edge device "dumb").

Environment: Any always-on Linux machine on the same LAN (a "Linux Mini PC"
in the original write-up).

API Framework: FastAPI, HTTP REST throughout (no WebSockets currently used).

AI Orchestration (unchanged from the original Jarvis Edge Node design):
  - Transcription: local ASR (faster-whisper, CPU).
  - Fast LLM tier: lightweight model via Ollama for an immediate reply.
  - Heavy LLM tier: larger model for background structuring — extracted
    to-dos land in the Command Center's Todo List.

Ambient Home / Tapo control: the backend, not the ESP32, speaks the Tapo
KLAP local protocol (via the `python-kasa` library) to each bulb's own LAN
IP. The device's Ambient Home grid only ever calls simple REST endpoints on
the backend (`/tapo/zones/*`) — the tricky auth/encryption handshake lives
in a maintained library on the server, not hand-rolled firmware crypto.

Communication: Paho-MQTT pushes the Jarvis Voice Capture confirmation text
to the ESP32 the moment the fast-tier reply is ready.

2.3 Mobile Bridge (Tasker on the paired Android phone)

Role: Notification transmitter — no app development required, just a Tasker
profile using a BLE/GATT plugin.

Mechanism: Tasker watches for incoming Android notifications (SMS, missed
call, high-priority app alerts) and writes a compact JSON payload to the
ESP32's BLE notification characteristic (schema + setup notes in
firmware/include/ble_notifications.h). The ESP32 advertises as "House
Phone".

2.4 Administration Frontend ("Command Center" — Vite / React)

Role: Configuration and long-form review — anything too fiddly for a 3.5"
touchscreen with an on-screen keyboard lives here instead: Tapo zone setup
(bulb IPs/rooms), the Todo List, prompt engineering, JARVIS 3.0 integration
status, and Ollama/MQTT/Tapo account settings.

Stack: Vite + React, Tailwind CSS, `react-router-dom`, `framer-motion`.

3. User Interface & Experience (UI/UX)

"Digital Sanctuary" principle: when you're home, the House Phone should be
enough — no unlocking your actual phone for a light switch, a timer, or the
gist of a text message. The UI stays a five-tile swipeable carousel (no
nested menus), high-contrast dark theme:

Persistent Status Bar: WiFi, battery, upload-queue badge.

Card 1 — Ambient Home (default/home tile): a grid of Tapo bulb zones. Tap a
zone to toggle it on/off; long-press for a brightness slider; a top-corner
"All Off" button clears every zone at once. Zones (name/room/IP) are
configured from the Command Center's Ambient Home page, not on-device.

Card 2 — Landline Feed: a scrollable list of BLE-relayed phone
notifications (app / title / text). Tap a card to dismiss it, same gesture
as swiping away a real phone notification.

Card 3 — Timers & Alarms: three cooking presets (+5 Min / +15 Min / Pasta
10 Min) driving a countdown display, plus a bedside wall-clock alarm
(hour/minute rollers + enable switch). Both share the onboard buzzer; the
whole tile flashes red and blocks touch until dismissed ("Tap to silence")
while ringing.

Card 4 — Jarvis Voice Capture: unchanged from the original design — a large
Record button and a confirmation label fed by the backend's fast-tier reply
over MQTT. Holding the physical BOOT button still works too (see 4.1).

Card 5 — Settings: on-device WiFi/backend/MQTT config, Ambient VAD and
power-saving toggles, and screen lock/timeout — unchanged from the original
Jarvis Edge Node Settings tile. (Tapo account credentials and zone CRUD live
in the Command Center instead, since they need a full keyboard and are
edited far less often.)

4. Core Workflows

4.1 Audio Capture & Offline Queuing (unchanged)

Holding the physical BOOT button (or tapping Record on Card 4) kills the
display backlight (BOOT only) and streams I2S microphone audio into PSRAM;
releasing/tapping again writes the buffered audio to `/queue/*.wav` on the
SD card. See firmware/src/mic_capture.cpp and plaud_mode.cpp.

4.2 Auto-Sync & Voice Capture Confirmation (unchanged)

The ESP32's background sync task uploads queued `.wav` files to
`POST /upload/audio`; the backend transcribes, gets a fast-tier reply, and
publishes it over MQTT (`jarvis/ui/feed`) for Card 4 to display immediately.
The heavy tier then runs in the background and any extracted to-dos land in
the Command Center's Todo List (Command-Center-only, no on-device tile).

4.3 Ambient Home (Tapo control)

1. User taps/long-presses a zone tile on Card 1.
2. Firmware fires a fire-and-forget POST to the backend
   (`/tapo/zones/{id}/toggle` or `/brightness`).
3. The backend connects directly to that bulb's LAN IP via `python-kasa`
   (KLAP protocol) and applies the change.
4. Every few seconds, the firmware polls `GET /tapo/zones` and repaints the
   grid from the bulbs' actual reported state — so the grid stays correct
   even if a bulb was changed from the Tapo app instead.

4.4 Landline Feed (BLE notification relay)

1. Tasker on the paired phone detects a new Android notification.
2. Tasker writes a JSON payload to the ESP32's BLE characteristic.
3. The BLE write callback parses it and pushes it into an in-RAM ring
   buffer (`firmware/src/ble_notifications.cpp`) — nothing is sent to the
   backend or persisted to SD; it's ephemeral, matching a real phone's
   notification shade.
4. Card 2 polls for new arrivals once per `loop()` iteration and refreshes.

4.5 Timers & Alarms

Countdown presets and the bedside alarm are both handled entirely on-device
(`firmware/src/timers_alarms.cpp`) — no backend round-trip. The wall-clock
alarm compares against NTP-synced local time (via the same
`configTzTime()` call `wifi_manager.cpp` already made on WiFi connect), so
it will not be accurate until the device has synced time at least once
after a reboot.

5. Hardware Notes Carried Over From Jarvis Edge Node

- The onboard mic and the microSD slot share hardware and cannot be used
  simultaneously — recordings are buffered fully in PSRAM during capture
  and only touch the SD card once, after the I2S driver is uninstalled.
- The buzzer pin used by Timers & Alarms (`TIMER_BUZZER_PIN` in
  firmware/src/timers_alarms.cpp) has **not** been confirmed against a real
  House Phone board revision — verify it before flashing, same caveat that
  already applied to the SD card pin map.
